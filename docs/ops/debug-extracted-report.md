## Корень 1: `limit_not_in_quote` (16-18 ячеек, главный убийца)

**Репро.** `specs/ACC-7201.json`, пункт 6.2: `limit="1500000.00"`, цитата
содержит `«...превышала $1,500,000.00 за период...»`.
`_limit_forms("1500000.00")` даёт `{"1500000.00", "1500000"}` — без запятых.
Ни одна форма не встречается в `"$1,500,000.00"` как подстрока: комма между
группами цифр ломает совпадение.

**Доказательство корня.** Скрипт по всем 12 заёмщикам (`specs_extract._check`
без выполнения LLM, только по уже сохранённым `specs/*.json` +
`dossier/*.json`) показал: 18 ячеек с `limit_not_in_quote`, во ВСЕХ 18 порог в
цитате написан с `$`-префиксом и запятыми-разделителями тысяч
(`$500,000.00`, `$3,500,000.00`, ... `$8,700,000.00`) — ни одного случая с
другим разделителем (пробел/nbsp) в этом датасете.

**Фикс.** `specs_extract._limit_in_quote` теперь дополнительно сверяет формы
порога с цитатой, у которой сняты разделители тысяч между группами цифр
(запятая, обычный/неразрывный/узкий неразрывный пробел) — но только для ЭТОЙ
проверки; `verify_quote` (цитата = реальный текст договора) не тронут и
продолжает требовать точное совпадение. Порог по-прежнему обязан реально
присутствовать в верифицированной цитате — просто без чувствительности к
форматированию числа.

**Тест.** `tests/test_specs_extract.py::test_limit_with_thousands_separator_in_quote_is_valid`
(падал до фикса).

**Результат.** Прямой прогон `_check` по всем 36 ячейкам публичного набора:
`limit_not_in_quote` → 0 (было 18); ячеек `OK` → 31 (было 13).

## Корень 2: `quote_unverified` (5 ячеек) — два разных механизма

Изначальная гипотеза («сшивка текста») подтвердилась для 3 из 5, для

### 2a. Утечка номера страницы (P4 6.3, P5 6.3, P8 6.3) — сшивка, исправлено

**Репро.** Сырой вывод `pypdf.PdfReader(...).extract_text()` для
`61dfc54675dc.pdf` (P8), страница 6: `"...превышали \n6"` — номер страницы
лежит последней строкой сырого текста, ОТДЕЛЬНО от тела (с `\n` перед ним).
`route.full_text` сшивает страницы через `"\n".join(chunks)`, `_normalize`
схлопывает `\n` в пробел — итоговый текст получает `"...превышали 6 0.04x
от выручки..."`: голая цифра `6` (footer) вклинивается ровно в середину
предложения, потому что ковенант делится по границе страницы 6/7.

**Доказательство корня.** Проверено на 3 реальных PDF (P4/P5/P8): у ВСЕХ
трёх страница, где рвётся цитата модели, оканчивается сырым текстом вида
`"<тело> \n<номер этой же страницы>"`. У P8 отдельно проверено: КАЖДАЯ из 18
страниц документа оканчивается голым номером, совпадающим с её порядковым
индексом (1..18) — систематический паттерн футера, не случайность.

**Фикс.** `pdftext._strip_page_footer(raw_text, n)`: снимает последнюю
строку сырого (до `_normalize`) текста страницы, только если она ТОЧНО равна
`str(n)`. Работает на сырых данных намеренно — после `_normalize` граница
строки теряется и число рискует быть частью суммы/БИН на той же строке
(первая версия фикса ловила это на странице 18 документа P8: `"...БИН
586673225134 18"` — попытка отличить футер от суммы по «не цифра перед
пробелом» ложно сработала на БИН). `TEXT_VERSION` 1→2, `DOSSIER_VERSION`
3→4 — только пересборка текста, без обращения к LLM (цитата спеки уже в
кэше и не требует повторного вызова модели: `specs_extract._check` гоняется
заново на КАЖДЫЙ вызов `extract_specs`, читая уже закэшированные
`covenants`, — так и было спроектировано с задачи 23).

**Тест.** `tests/test_pdftext.py::test_page_footer_number_is_stripped` на
реальном `61dfc54675dc.pdf` (падал до фикса).

**Результат.** Прямая проверка `verify_quote` на пересобранном тексте: P4
6.3, P5 6.3, P8 6.3 → `True` (было `False`).

### 2b. B1 6.2 — опечатка модели в цитате, НЕ сшивка

Цитата модели: `«...по аудированной отчётОСТИ Заёмщика...»`
(без буквы «н»). Реальный текст договора (страница 5, мидстраницы, далеко
от любой границы): `«...по аудированной отчётНОСТИ Заёмщика...»`. Разница —
ровно одна пропущенная буква, не рядом с границей страницы, не футер, не
разделитель. Это галлюцинация модели при генерации цитаты, а не повреждение
текста при извлечении. Чинить нечем без ослабления `verify_quote` (что
запрещено) или без перегенерации спеки моделью (промпты не трогать).
Оставлено как задокументированный остаток.

### 2c. P3 6.2 — разрыв слова pypdf, НЕ сшивка

Сырой текст страницы 6 документа `85afaaca89ad.pdf` (P3) содержит
`«...Минимальный объём по статье «Выручка». У словием предоставления...»`
— слово «Условием» разорвано пробелом ПОСЕРЕДИНЕ СТРАНИЦЫ (не на границе
страниц: до и после — один и тот же `page.extract_text()` без `\n`).
Проверено: это не системный паттерн (единственное такое разбиение на всей
странице, остальные начала предложений после точки не разорваны) — похоже
на квирк pypdf при извлечении конкретного глифового прогона (может быть,
из-за стилизации первой буквы). Фикс потребовал бы либо схлопывания ВСЕХ
внутренних пробелов при сравнении (риск: ослабляет word-boundary защиту
`verify_quote` от инъекции — произвольная склейка токенов через `join`
случайных фрагментов текста начинает матчиться), либо угадывания
конкретного слова (подгонка под ключ). Оставлено как задокументированный
остаток.

## Корень 3: конфликтующие реклассификации — сшивка, исправлено (но не спасает ячейку)

**Репро.** `facts/ACC-7201.json` (B1), `reclass`: ДВА документа
реклассифицируют ОДНУ операцию (`TXN-B1-0020`, контрагент Irtysh Advisory
Bureau) по-разному — один в `INTEREST` (содержательное решение с
обоснованием), второй в `OTHER` (аудиторская пометка «сумма отобрана для
проверки, вывод — в другом отчёте», куда модель вынуждена подставить
СУЩЕСТВУЮЩУЮ категорию, потому что схема требует `to_category` всегда).
`engine.prepare_rows` применял решения по индексу массива и брал ПОСЛЕДНЕЕ
совпавшее — победитель зависел от порядка документов в досье, а не от
содержания. `facts_extract.py` сортирует `reclass` по `(txn, counterparty)`;
у обеих записей `txn=None`, `counterparty` одинаковый — сортировка не
различает их, порядок остаётся исходным (порядком обработки документов).

**Доказательство корня.** Прямой расчёт: с исходным кодом `TXN-B1-0020`
после `prepare_rows` получал категорию `OTHER` (должен `INTEREST`).
`evidence.candidates()` независимо от `prepare_rows` строит по кандидату НА
КАЖДУЮ совпавшую запись реклассификации — оба конфликтующих решения
попадали в перебор, но откат «пустого» (уже перебитого) решения не менял
факт, поэтому «улика = 0» была следствием другого механизма (см. ниже), не
самого перебора кандидатов.

**Фикс.** `prepare_rows` собирает ВСЕ совпавшие для строки решения и
выбирает победителя по специфичности: явный `txn`-матч важнее матча по
контрагенту (иначе решение по контрагенту цепляет вообще все его операции
без разбора); при равной специфичности — содержательная категория важнее
`OTHER` (корзина неизвестного из `taxonomy.py`, не реальное решение
документа); финальный тай-брейк — индекс, для детерминизма. Не требует
изменений в `evidence.py`: если проигравшая запись «отменяется»
(`undo_reclass`), победителем автоматически остаётся выигравшая — эффект
нулевой, как и должно быть.

**Тест.** Два теста в `tests/test_engine.py`:
`test_prepare_rows_conflicting_reclass_prefers_specific_category_over_other`,
`test_prepare_rows_conflicting_reclass_prefers_txn_match_over_counterparty`
(оба падали до фикса; второй проверяет оба порядка следования решений).

**Почему это НЕ спасает B1 6.1 (важная оговорка).** После фикса
`TXN-B1-0020` действительно получает `INTEREST` (совпадает с ключом:
эталон — `{"txn": "TXN-B1-0020", "to": "INTEREST"}`). Но `actual` для B1 6.1
остаётся далёким от ключа (54.78/39.30 против 1.68) — потому что
ДОМИНИРУЮЩАЯ причина расхождения не реклассификация, а выбор роллапа EBITDA
в самой спеке: извлечённая метрика — `sub(agg(REVENUE, in), agg(OPEX_TOTAL,
out))` (`OPEX_TOTAL` ≈ 93.5M), эталонный шаблон `templates._EBITDA` —
`sub(agg(REVENUE, in), agg(OTHER_OPEX, out))` (`OTHER_OPEX` ≈ 6.17M).
Проверено арифметически: `(REVENUE − OTHER_OPEX) / (INTEREST + 592,296.10)`
= `3,575,342.12 / 2,133,129.39` = **1.676** — с точностью до округления
`1.68` из ключа. Это выбор модели при чтении текста договора («Операционных
расходов» — широкая формулировка, допускающая обе трактовки по инструкции
`SPECS_PROMPT`), не ошибка сшивки. Промпт не трогаю — оставлено как
задокументированный остаток.

## Корень 4: `counterparty_in` со строковым аргументом — сшивка, исправлено

**Репро.** `specs/ACC-7809.json` (P9), пункт 6.3:
`metric: "agg(ALL, out, counterparty_in('related_parties'))"`. Грамматика
принимала только голый идентификатор (`related_parties`) или список
(`['Имя', ...]`) — строковый литерал `'related_parties'` не подходил ни под
одну ветку, `_build_filter` ронял `DslError: неизвестный фильтр
counterparty_in/1`.

**Фикс.** `_build_filter` для `counterparty_in` со строковым аргументом:
если строка совпадает с именем известного множества
(`related_parties`/`unrestricted_subsidiaries`) — то же множество (модель
просто выбрала не ту синтаксическую форму для того же смысла); иначе —
список из одного контрагента (та же семантика, что уже работает для формы
`['Имя']`). Это чтение уже поддержанных форм через альтернативный синтаксис,
не новая семантика.

**Тест.** `tests/test_dsl.py::test_parse_counterparty_in_quoted_set_name_equals_bare_keyword`,
`test_parse_counterparty_in_quoted_single_name_is_singleton_list` (оба
падали до фикса).

**Не тронуто намеренно.** `P7 6.1`: `ratio(a, add(b), c)` — 3 аргумента
вместо 2 (модель вложила `add()` только вокруг второго слагаемого, а не
вокруг суммы двух). Это некорректный DSL, а не форма, которую можно
однозначно переинтерпретировать — лестница фолбэков отрабатывает как надо
(`invalid_spec` с внятным алярмом), оставлено как есть по указанию задачи.

**Побочно найдено, НЕ покрыто фиксом.** `specs/ACC-7805.json` (P5), 6.3:
`counterparty_in(['related_parties'])` — та же путаница синтаксиса, но на
уровне СПИСКА (список из одного элемента, совпадающего с именем множества),
а не строки. Технически симметричное расширение возможно (тот же принцип:
единственный элемент списка, совпадающий с именем множества, — то же
множество), но не сделано в рамках этой сессии — не было явно санкционировано
в задаче, добавляю в остатки на рассмотрение.

## Корень 5: `paired_payment` fx-курс без границ интервала — сшивка, ФИКС ЕСТЬ, НЕ АКТИВИРОВАН

Изначальная гипотеза задачи («fx_uncovered EUR — вероятно баланс, а не баг
этого прогона») **не подтвердилась**: expected-режим на ТОМ ЖЕ архиве даёт
**0** алярмов `fx_uncovered` (только мягкий `fx_unbounded_interval` через
донора); extracted-режим — больше десятка. Это реальный баг extracted-пути.

**Репро.** `facts/ACC-7803.json` (P3): курс EUR,
`derivation: "paired_payment"`, `effective_from = effective_to =
"2025-12-31"` — курс выведен из ОДНОЙ пары зеркальных платежей, но модель
проставила в границы интервала дату этого платежа. `fx.pick_rate` берёт курс
только для дат, попадающих в `[effective_from, effective_to]` — с интервалом
в один день курс не покрывает НИ ОДНУ дату другого заёмщика (в expected-режиме
эталонная запись для того же курса имеет `effective_from = effective_to =
""` — пусто, «без известных границ», и `fx._covers` трактует пустые границы
как «действует всегда»).

**Доказательство корня.** `eval/expected_extraction.py`, комментарий у
записи P3: «Курс выведен из пары зеркальных платежей, интервал в документе
не указан — пустые границы». Прогон `solve.main(archive,
facts_source="expected")` на том же архиве подтвердил: 0 `fx_uncovered`.

**Фикс.** `facts_extract._merge_doc`: для `derivation == "paired_payment"`
границы интервала принудительно снимаются (`effective_from = effective_to =
""`), независимо от того, что вернула модель — это следствие ТИПА вывода
(курс из одного наблюдения структурно не имеет документально заявленного
периода действия), а не цитаты. `derivation == "table"` не тронут — там
интервал документально заявлен и должен оставаться как есть.

**Тест.** `tests/test_facts_extract.py::test_paired_payment_fx_rate_has_no_interval_bounds`,
`test_table_fx_rate_keeps_its_interval_bounds` (первый падал до фикса,
второй — регрессия на то, что `table` не трогается).

**Почему не активирован.** `FACTS_VERSION` оборачивает `build()` целиком,
включая сам `llm.call()` — в отличие от `specs_extract`, где верификация
цитаты (`_check`) гоняется заново на каждый вызов НЕЗАВИСИМО от кэша LLM.
Подъём `FACTS_VERSION` форсирует новый вызов модели по КАЖДОМУ документу
(текст изменился из-за фикса футера страницы — п. 2a — значит меняется хеш
промпта, и кэш `llm.call` промахивается). На попытке активации это вызвало
всплеск платных вызовов и уткнулось в исчерпанный баланс Anthropic API
(«Your credit balance is too low») — все 12 заёмщиков получили
`facts_extraction_failed` по 3-5 документам, факты частично опустели.
Откатил (`FACTS_VERSION` обратно на 1) — код фикса остался, задокументировал
причину прямо в файле. **Рекомендация**: активировать отдельным шагом с
пополненным балансом, в идеале — после переноса верификации/производных
поправок `facts_extract` за пределы кэша `build()` по образцу
`specs_extract` (структурный рефакторинг, отдельная задача).

### Что именно активирует подъём `FACTS_VERSION` и во сколько это встанет

**Что активируется.** Поднятие `FACTS_VERSION` форсирует `build()` заново
для ВСЕХ 12 заёмщиков (43 документа суммарно — см. подсчёт по `dossier/*.json`
ниже), поскольку текст документов изменился из-за фикса футера страницы
(корень 2a) — меняется промпт, и кэш `llm.call` по хешу промахивается
независимо от того, какой конкретно документ реально нуждается в переизвлечении.
Это активирует НЕ ТОЛЬКО фикс 5 (границы `paired_payment`), но и
пере-верификацию ВСЕХ цитат `facts_extract` (`related_parties`,
`unrestricted_subsidiaries`, `reclass`, `exclude`, `amount_override`,
`fx_rates`, `numeric_facts`) против исправленного текста — то есть заодно
может (но не гарантированно) починить часть `quote_unverified`-алярмов на
`doc_facts`, которые я не трогал намеренно (см. корень 2, разбор для B1).

**Оценка стоимости.** Офлайн-подсчёт по кэшу (без единого сетевого вызова):
43 документа (`dossier/*.json`), суммарно ≈ 691,941 символ текста ≈ 197,700
входных токенов (по грубой оценке 3.5 симв/токен для смешанного ru/en
текста); средний закэшированный ответ facts-схемы — 43 сохранённых JSON в
`work/llm_cache`, средний размер 2,293 символа ≈ 655 выходных токенов на
вызов, то есть ≈ 28,200 выходных токенов суммарно. По ценам из `llm.py`
(`PRICE_IN=$3/млн`, `PRICE_OUT=$15/млн` — это консервативная оценка, в
комментарии кода помечена как цена Sonnet 5, реальная модель — Haiku 4.5,
дешевле) — **≈ $1.02** за полную ре-экстракцию. Это дёшево само по себе:
инцидент на боевом прогоне — не из-за дороговизны фикса, а потому что
БАЛАНС АККАУНТА Anthropic был близок к нулю ДО этого вызова (специфика/
плюс прогонов остальной команды в этом же ключе, не только моих). При
положительном балансе ≥$2 активация должна пройти без повторного инцидента
по бюджету — но НЕ без риска качества (см. ниже).

**Риск качества, отдельный от риска бюджета.** Определённость (детерминизм)
в этом пайплайне — только от кэша по содержимому, НЕ от `temperature=0`
(инвариант из CLAUDE.md). Живой повторный вызов на слегка изменённый промпт
не гарантирует ТОТ ЖЕ ответ модели, что и раньше — это подтвердилось прямо
на неудавшейся попытке активации: `facts/ACC-7803.json` (P3) до неё содержал
валидный `fx_rate` (тот самый, что чинит фикс 5), а ПОСЛЕ повторного вызова
(до того как упёрлось в бюджет) — `fx_rates: []`, модель в этот раз вообще
не извлекла курс из того же документа. Значит активация — это не только
трата денег, но и лотерея по качеству: часть уже работающих фактов может
пропасть, часть сломанных — починиться, в непредсказуемой пропорции. Это
дополнительный аргумент за структурный рефакторинг (перенос верификации за
пределы кэша `build()`, как уже сделано в `specs_extract`) вместо простого
пополнения баланса и повторной попытки.

## Побочная находка: `work/<hash>/trace` и `out/submission.json` не разделены по facts_source

`util.workdir(ds_hash)` и `util.OUT` не учитывают `facts_source` — оба
режима (`expected`/`extracted`) на одном архиве пишут в ОДНИ И ТЕ ЖЕ
`work/<hash>/trace/*.json` и `out/submission.json`. В начале сессии поймал
это вживую: `trace/B1.6.2.json` сменил содержимое между двумя чтениями (был
extracted-путь `path=prior, tier=2`, стал expected-путь `path=dsl, tier=0`)
— кто-то параллельно прогнал expected-режим на этом архиве. Артефакты
документного слоя (`specs/`, `facts/`, `dossier/`, `text/`, `route/`)
не пострадали — их expected-режим не трогает. Для этой задачи не критично
(работал по стабильным артефактам), но при параллельных прогонах разных
режимов на одном архиве — риск смешать результат. Стоит завести отдельным
пунктом (например, ключевать `workdir`/`OUT` по `facts_source` или хотя бы
предупреждать при коллизии).

## Классы оставшихся расхождений (не сшивка, качество извлечения, промпт-governed)

1. **related_parties из KYC-таблиц голосующих прав теряется целиком.**
   Модель цитирует таблицу многоточием (`"Aktau Holdings LLP 34.5% ...
   Организации, в которых Группа владеет 20.0%..."`) — не дословная цитата,
   `verify_quote` корректно отбрасывает факт (P1: `Aktau Holdings LLP`
   пропал; P7: `Atyrau Holding Group LLP` пропал). Затрагивает 6.1/6.3 у
   P1, P7 и, вероятно, P9.
2. **related_parties threshold не применяется моделью.** Модель извлекает
   `<company>_voting_rights_pct` для КАЖДОЙ упомянутой компании И
   `related_party_threshold_pct` отдельными numeric_facts (верно прочитала
   правило), но заполняет `related_parties` списком ВСЕХ упомянутых
   компаний, не сверяя процент с порогом (B1: включены Irtysh 18.6% и
   Pavlodar 12.5%, при пороге 20% — оба должны быть исключены). Это прямое
   нарушение архитектурного принципа «LLM читает, код считает»: сравнение
   с порогом — арифметика, а её делает модель. Ключи `numeric_facts`
   придуманы моделью (`snake_case`, "если нужного ключа нет — придумай") —
   не стабильный контракт, на который можно опереться в коде без риска
   переусложнить мост под конкретные названия.
3. **Обобщённая фраза вместо ключевого слова `related_parties`.**
   `counterparty_in(['аффилированные лица'])` (P2, P8),
   `counterparty_in(['связанные стороны'])` (P6) — модель иногда
   переводит понятие «связанные/аффилированные стороны» буквально как имя
   контрагента вместо использования зарезервированного идентификатора
   `related_parties`, хотя в ДРУГИХ сценариях (B1, P1, P7) правильно
   использует голое ключевое слово. Непоследовательность модели, не
   формат — код уже поддерживает ОБЕ правильные формы (голое слово, список
   имён, и теперь строку-алиас из корня 4).
4. **fx_uncovered EUR** — было ошибочно списано в исходной гипотезе задачи
   на «баланс»; на деле реальный баг (корень 5), фикс есть, не активирован
   из-за бюджета API.
