# Активационный шаг: подъём FACTS_VERSION и ROUTE_VERSION

Единая точка чек-листа для двух версий, сознательно НЕ поднятых в
debug-волне (`f0e1764`..`cb66d5e` + фикс-раунд по ревью), чтобы не жечь
бюджет Anthropic API на уже закэшированном ПУБЛИЧНОМ workdir
(`work/f2c65d2cfc8d8527`). Выполнять этот шаг ТОЛЬКО после подтверждённого
пополнения баланса аккаунта.

На СВЕЖЕМ workdir (нет файла на диске — например, приватный датасет 9
августа) этот шаг не нужен вовсе: `build()` выполняется безусловно при
первом обращении, оба фикса (paired_payment, футер страницы) сработают
автоматически без явного подъёма версий. Чек-лист актуален только для
повторного прогона на ЭТОМ ЖЕ (публичном) архиве/workdir.

## Что поднимать

1. `solution/facts_extract.py`: `FACTS_VERSION = 1` → `2`. Убрать (или
   переформулировать в прошедшем времени) сопровождающий комментарий —
   он объясняет, почему версия НЕ поднята; после подъёма он вводит в
   заблуждение.
2. `solution/route.py`: `ROUTE_VERSION = 1` → `2`. Аналогично —
   актуализировать комментарий.

## Что каждый фикс активирует

- **FACTS_VERSION → 2**: `facts_extract._merge_doc` пересчитает
  `effective_from`/`effective_to` для `derivation == "paired_payment"`
  (снимет границы интервала) — чинит `fx_uncovered` там, где курс из пары
  зеркальных платежей раньше покрывал только день платежа (см. корень 5 в
  `debug-extracted-report.md`). Побочно: ВСЕ цитаты `facts_extract`
  (`related_parties`, `reclass`, `exclude`, `amount_override`, `fx_rates`,
  `numeric_facts`) переверифицируются против исправленного текста (футер
  страницы снят в `TEXT_VERSION=2`) — может (не гарантированно) снять часть
  `quote_unverified` на `doc_facts`, не гарантированно чинит
  KYC-таблицы-с-многоточием (это отдельная, не сшивочная причина — см.
  корень «related_parties» в отчёте).
- **ROUTE_VERSION → 2**: `route.route_doc` пересчитает META (`doc_type`,
  `date`, `edition`) и, при неоднозначной привязке, WHOSE — против текста
  без футера страницы. Ожидаемый эффект минимален (см. комментарий в коде):
  футер-номер страницы (1-3 символа в конце текста) практически не может
  сдвинуть META-решение, которое читает первую страницу целиком, а не
  предложение на границе. Бампится в первую очередь для согласованности
  версий (вход изменился — стадия обязана заявить об этом явно), не
  потому что от неё ожидается score-эффект.

## Ожидаемая стоимость (офлайн-оценка по кэшу, без единого сетевого вызова)

Ценам из `solution/llm.py` (`PRICE_IN=$3/млн`, `PRICE_OUT=$15/млн` —
консервативная оценка, в коде помечена как цена Sonnet 5; реальная модель
`claude-haiku-4-5-20251001` дешевле):

| Стадия | Вызовов | Вход (токены, оценка) | Выход (токены, оценка) | Оценка $ |
|---|---|---|---|---|
| `facts_extract` (43 документа, полный текст) | 43 | ≈197,700 | ≈28,200 | ≈$1.02 |
| `route` (META, первая страница; WHOSE — 0 на этом датасете) | 67 | ≈36,850 | ≈1,270 | ≈$0.13 |
| **Итого** | **110** | **≈234,550** | **≈29,470** | **≈$1.15** |

Оценка входных/выходных токенов — по среднему размеру уже закэшированных
ответов (`work/llm_cache/*.json`) и среднему размеру текста на входе
(`chars/3.5`), без сетевых вызовов. Реальная стоимость может отличаться
(разные модели/цены), но порядок величины — единицы долларов, не десятки.

## Риск НЕ бюджетный, а качества (недетерминизм живого перевызова)

Детерминизм в этом пайплайне — только от content-addressed кэша
(`sha256(model + prompt + json_schema + schema_version)`), НЕ от
`temperature=0` (инвариант CLAUDE.md). Живой повторный вызов на изменённый
промпт (даже минимально — снят футер) не гарантирует ТОТ ЖЕ ответ модели,
что и раньше. Прямое наблюдение из неудавшейся попытки активации в
debug-волне: `facts/ACC-7803.json` (P3) ДО повторного вызова содержал
валидный `fx_rate` (курс EUR из пары зеркальных платежей — именно то, что
чинит фикс 5); ПОСЛЕ повторного вызова (до того как упёрлось в бюджет) —
`fx_rates: []`, модель в этот раз вообще не извлекла курс из того же
документа. То есть активация — это не только трата денег, но и лотерея:
часть уже рабочих фактов может пропасть, часть сломанных — починиться, в
непредсказуемой пропорции. Полностью безопасный вариант — структурный
рефакторинг `facts_extract`/`route` по образцу `specs_extract` (вынести
верификацию/производные поправки за пределы кэша `build()`, кэшировать
только сырой ответ LLM) — отдельная задача, не входит в этот чек-лист.

## Кассета заморожена под LLM_PROVIDER=gemini

`eval/cassette` собрана из прогона с `LLM_PROVIDER=gemini` (модель —
`GEMINI_MODEL` в `solution/llm.py`, см. [[llm-provider-gemini-switch]]).
Ключ кассеты — `sha256(model + prompt + json_schema + schema_version)`, а
`model` зависит от `LLM_PROVIDER` (дефолт в коде — `anthropic`). Любой
офлайн-путь (`LLM_OFFLINE=1`), запущенный БЕЗ явного `LLM_PROVIDER=gemini`,
промахивается кассетой на 100% ключей — не громким `CassetteMiss` по
каждому, а молчаливым обнулением офлайн-гейта до фолбэков/skip.

Выставлено точечно, НЕ блоком на весь `pytest`: `.github/workflows/ci.yml`
(шаг `run.sh end-to-end`) и обе строки `eval/invariants.py` в
`make eval-offline` ставят `LLM_PROVIDER=gemini` на весь процесс — это
отдельные однократные прогоны пайплайна без мок-инъекций. Строка
`uv run pytest -q` в `make eval-offline` эту переменную НЕ ставит:
`tests/test_faults.py` намеренно снимает `LLM_OFFLINE` и мокает
`llm._create` (anthropic-путь) для симуляции мёртвой сети, и глобальный
`LLM_PROVIDER=gemini` увёл бы вызов мимо мока в реальную сеть Gemini
(живой 403 без ключа — проверено при ревизии этого чек-листа). Офлайн-гейт
extracted-пути (`tests/test_extracted_gate.py`) ставит переменную сам,
точечно, через `monkeypatch.setenv` внутри теста. При добавлении новых
офлайн-путей — так же точечно, не блоком на весь `pytest`.

## Команда верификации

```bash
set -a; source .env; set +a
zsh .superpowers/sdd/2026-08-06-halyk-pipeline/run_llm_test.sh
```

Смотреть итог в `.superpowers/sdd/2026-08-06-halyk-pipeline/llm-run.log`:
поячеечная таблица в конце первого FAILED-теста (если floor не пройден) или
в PASSED-выводе (если пройден). Сравнить с базовым чистым замером **19.50/36.00**
(зафиксирован в `debug-extracted-report.md` до активации) — любое отклонение
вниз для конкретной ячейки, не объяснённое фиксом 5, скорее всего
недетерминизм повторного вызова (см. риск выше), а не новый баг.

## Порядок действий

1. Подтвердить пополнение баланса (например, пробный `rtk gain` или любой
   дешёвый живой вызов вне этого пайплайна — НЕ тратить бюджет на сам
   пайплайн для проверки баланса).
2. Поднять обе версии (см. «Что поднимать»), актуализировать комментарии.
3. `make check` (офлайн-часть, без сети) — зелёный перед боевым прогоном.
4. Запустить команду верификации выше.
5. Сравнить итоговый скор и поячеечную таблицу с 19.50/36.00 из
   `debug-extracted-report.md`; отдельно отметить: (а) исчез ли
   `fx_uncovered` EUR (ожидаемый эффект фикса 5), (б) не просели ли ранее
   рабочие ячейки (риск недетерминизма, см. выше).
6. Если floor всё ещё не пройден и остаток разрыва совпадает с классами
   «качество извлечения» из `debug-extracted-report.md` — это ожидаемо,
   активационный шаг не предназначен их закрывать.

## Отложено тем же бюджетом: пороги FLOORS (PR #7)

`tests/test_mutations_ledger.py::FLOORS` — минимальное восстановление,
которого требуем от второго яруса категоризации по мутированным описаниям
(holdout для пяти категорий, у которых естественного holdout'а нет:
`REVENUE`, `CAPEX`, `OTHER_OPEX`, `CONSULTING`, `FINANCING`).

**Текущее состояние:** все пять стоят на `1.00`, но замер сделан
`LLM_PROVIDER=gemini`, модель `gemini-3.6-flash` (2026-08-08). На дефолтном
провайдере (`anthropic`, `claude-haiku-4-5`) пороги **не снимались** —
Anthropic-баланса не было, как и для активационного шага выше.

**Когда это неважно.** Если боевой прогон 9 августа идёт на Gemini, пороги
сняты на боевой модели и пересъём не нужен. Проверить перед окном, каким
значением `LLM_PROVIDER` пойдёт прогон.

**Когда пересъём обязателен.** Если прогон идёт на `anthropic`. Числа
модельно-специфичны, и падение теста на anthropic-прогоне будет означать
«на haiku восстановление хуже, чем на gemini», а не дефект промпта —
прежде чем править `CAT_PROMPT`, сверьтесь, каким провайдером идёт прогон.

**Команда пересъёма:**

```bash
set -a; source .env; set +a
uv run pytest tests/test_mutations_ledger.py -m llm -q -s -k recovery
```

Значения берутся из строки «ХУДШЕЕ ПО ТРЁМ» в выводе, округляются вниз до
сотых и вписываются в `FLOORS` вместе с датой, провайдером и моделью.
`REVENUE` и `OTHER_OPEX` стоят на `1.00` априори (обе входят в EBITDA, то
есть в каждую коэффициентную ячейку) — их просадка означает, что чинить
надо промпт, а не порог.

**Страж:** `test_all_floors_are_measured` (не llm, идёт в `make check` и в
CI) падает, пока хоть один порог `None`. Ставить `None` при пересъёме
безопасно — забыть вписать результат не получится.

**Известная граница замера.** На `gemini-2.5-flash` разовая диагностика
давала `OTHER_OPEX = 0.93`: промах на `Warehouse risk survey upkeep 2025`
→ `INSURANCE`. Это семантическая двусмысленность самого набора (страховой
сюрвей граничит со страхованием), а не дефект промпта. Если жёсткое `1.00`
по `OTHER_OPEX` не возьмётся на боевой модели — смотреть, на какой строке
промах, прежде чем трогать промпт.
