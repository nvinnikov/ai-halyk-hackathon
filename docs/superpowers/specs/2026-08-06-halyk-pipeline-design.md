## 1. Задача и ограничения

По каждому заёмщику из приватного архива нужно заполнить три компонента на каждый ковенант:
вердикт (`COMPLIANT` / `BREACH`), число `actual`, обосновывающее вердикт, и `evidence_txn_id` —
транзакцию-улику, если нарушение связано с конкретной операцией.

Шкала (`CASE.ru.md`, раздел 4):

| Компонент | Баллы | Правило |
|---|---|---|
| `status` | 0.50 | Точное совпадение с ключом |
| `actual` | 0.30 | `0.30 × max(0, 1 − e/0.05)`, где `e = \|наше − ключ\| / \|ключ\|` |
| `evidence_txn_id` | 0.20 | Точное совпадение. Если в ключе `null` — баллы убывают вместе с `actual` по той же шкале |

Ячейки взвешиваются по сложности (`CASE.ru.md:129`), веса участникам не сообщаются.

Ограничения:

- Приватный датасет: 9 августа 2026, 11:00 (Астана). Дедлайн: 14:00 того же дня. Окно — 3 часа.
- Время отправки — второй критерий после очков. Отправленные 80% бьют неотправленные 95%.
- Качество решения и кода — третий критерий.
- Ответы обязан сгенерировать собственный агент. Ручное заполнение и прогон через Claude Code /
  Codex запрещены (`rules.md`, раздел «Важные ограничения»).
- LLM внутри решения: Anthropic API.

## 3. Центральный принцип

**LLM читает, код считает.** Всё детерминируемое делается детерминированно. LLM трогает только
то, что требует понимания текста, и её выход всегда проходит через схему и грамматику до того,
как попасть в вычисление.

```
zip ─▶ extract ─▶ route ─▶ staleness ─▶ [пункт → спека]   ─▶ compute ─▶ verify ─▶ JSON
         │          │                    [факты досье]         │           │
         └ vision ──┘                    [добор категорий]     │           │
           (слепые страницы)                                   │           │
                                                               └─ трейс ───┘
```

Граница проведена там, где ошибка стоит дорого. Реклассификацию из аудиторского отчёта должна
вытащить модель — формулировки разные. Арифметику EBITDA и процентов модель не делает никогда:
`actual` стоит 0.30, плюс ещё 0.20 через ту же шкалу при `null` в ключе, то есть у коэффициентных
ковенантов цена числа фактически 0.50 — столько же, сколько у статуса.

### Детерминизм

`temperature=0` детерминизма не даёт: батчинг и роутинг на стороне провайдера возвращают разный
результат на идентичный запрос. Единственная реальная гарантия — content-addressed кэш:

```
key = sha256(model_id + prompt + json_schema + schema_version)
```

Из этого следует режим работы кэша — и он должен быть описан точно, иначе на месте возникнет
конфликт: раздел 8 отводит 11:35–13:15 под правки с переотправкой, а правки переизвлекают факты.

- **Кэш никогда не инвалидируется по времени, только по содержимому.** Ключ включает
  `schema_version` и текст промпта, поэтому правка промпта или схемы автоматически создаёт новые
  ключи и переизвлекает ровно то, что затронуто, не трогая остальное. Никакого «сбросить кэш»
  как операции не существует — это и есть механизм, позволяющий править в окне и не терять
  воспроизводимость.
- **«Заморозка» — это снимок, а не запрет.** Перед каждой отправкой каталог кэша копируется рядом
  с отправляемым JSON (`out/submission-<N>.json` + `out/cache-<N>/`). Любую отправленную попытку
  можно воспроизвести байт в байт задним числом, включая промежуточные.
- Ручное редактирование содержимого кэша запрещено: это единственный способ получить submission,
  который невозможно воспроизвести.

Мелкие ловушки, которые обязаны быть закрыты в коде:

- `round(2.675, 2) == 2.67` — банковское округление. Для `actual` использовать
  `Decimal.quantize(ROUND_HALF_UP)`. Допуск 5% это прощает почти всегда, но не на границе.
- Итерация по `set` меняет порядок между запусками: при двух равновероятных кандидатах в улику
  выберется разный. Всё сортировать перед использованием.
- Суммирование `float` в порядке словаря даёт разный последний бит. Суммировать в порядке `txn_id`.
- Self-consistency (N прогонов + голосование) детерминизм ломает. Вместо голосования — расхождение
  между прогонами пишется в отчёт алярмов. В трёхчасовом окне человек разрулит быстрее, чем
  мажоритарка угадает.

## 4. Судьба текущего кода

### 4.1. Правки в `engine.py`

- Отсутствующий курс валюты → `raise`, а не молчаливый 1.0. Сейчас `fx` задан только для P3, в
  леджере 15 EUR-строк у целевых заёмщиков (плюс 13 в фоновых счетах, до которых ковенанты не
  дотягиваются), распределены по 11 сценариям из 12 — без `EUR` только `P4`. Публичный скор
  держится лишь потому, что эти строки
  падают в категории, которых ковенанты их заёмщика не касаются.
- Парсинг `amount` устойчивый: `'1,234.56'`, `'(500.00)'`, `'n/a'`, пустое. Сейчас `float()` без
  защиты роняет весь прогон.
- Маршрутизация строк леджера по колонке `account_id`, а не по `txn_id.split("-")[1]`. Смена
  формата id сейчас даёт пустой список строк без единого исключения. Разбор `txn_id` не исчезает
  совсем — он нужен для связи со `scenario_id`, — но выполняется один раз в проверяемом месте
  (раздел 5.2), а не на каждом обращении к леджеру.
- Матч связанных сторон: сравнение по нормализованным токенам с минимальной длиной, а не
  двусторонний подстрочный `in`. Сейчас `norm('LLP') == ''`, а `'' in x` истинно всегда: пустая
  строка в `related_parties` (типовой выход LLM-слоя при провале KYC) делает связанными все
  расходные строки заёмщика. Логика продублирована в `covenants.py` в трёх местах — свести в одну.
- Положительные строки в расходных категориях (сторно, возвраты, ребейты) неттятся, а не
  выпадают. Управляется параметром `sign` в спеке (см. 5.3).

## 5. Контракты между стадиями

Стадии общаются только через файлы. Каждая идемпотентна, перезапуск пропускает готовое.

**Все производные артефакты живут под отпечатком входного архива.** Иначе идемпотентность
превращается в оружие: 9 августа пайплайн запускается на приватном архиве в каталоге, где уже
лежат публичные артефакты, и `work/ledger.parquet` с фиксированным именем будет признан готовым
и пропущен. То же с `work/dossier/<ACC>.json`, если `account_id` совпадут между наборами —
а они вполне могут, генератор один.

```
work/<dataset_hash>/index.json           scenario_id ↔ account_id, множество счетов
work/<dataset_hash>/ledger.parquet       разобранный и категоризированный леджер
work/<dataset_hash>/text/<hash>.json     страницы + флаг слепоты на каждую страницу
work/<dataset_hash>/vision/<hash>.p<N>.json  результат vision по странице
work/<dataset_hash>/route/<hash>.json    account_id, тип документа, дата, редакция
work/<dataset_hash>/dossier/<ACC>.json   сшитое досье
work/<dataset_hash>/specs/<ACC>.json     пункт → спека
work/<dataset_hash>/facts/<ACC>.json     факты досье
work/<dataset_hash>/trace/<ACC>.<clause>.json  трейс ячейки
out/submission.json
```

`dataset_hash` — хеш содержимого входного архива. `run.sh` печатает его первой строкой: если
9 августа в логе окажется знакомый хеш публичного набора, это видно сразу, а не по странным
результатам.

Внутри каталога идемпотентность работает по второму ключу — версии стадии, схемы и кода. Артефакт
считается готовым, только когда совпали и отпечаток входа, и версия произведшей его стадии;
инкремент версии стадии автоматически переизвлекает её выход, не трогая соседние. Механика та же,
что у кэша LLM (раздел 3), и по той же причине: инвалидация по содержимому, никогда по времени.

Кэш LLM, наоборот, **общий между наборами и отпечатком архива не разделяется** — он адресуется
содержимым промпта, поэтому одинаковый документ в двух наборах законно переиспользует ответ, а
разный даёт разные ключи. Разделять его по `dataset_hash` значило бы выбросить весь прогрев
9 августа в 11:00.

### 5.1. Извлечение текста и слепота

Слепота — свойство **страницы**, а не файла. Текущий детектор смотрит на файл целиком и ловит 1
случай из 4: у `2ed0b2ee4b57.pdf` 4374 символа на весь документ, файл выглядит нормальным, а
страницы 3–4 не отдают текстовый слой.

Правило: страница слепая, если после нормализации содержит меньше 200 символов **или** меньше 3
числовых токенов. Такие страницы рендерятся в изображение и отдаются vision-модели. Результат
кэшируется по хешу изображения.

### 5.2. Цепочка `txn_id` → `scenario_id` → `account_id`

Ответы в шаблоне лежат под `scenario_id` (`P1`), а документы знают только `account_id` (`ACC-7801`).
Связывает их леджер: по `CASE.ru.md:67-77` идентификатор каждой транзакции начинается со
`scenario_id` того заёмщика, на счёте которого она находится, и каждый `account_id` соответствует
ровно одному `scenario_id`.

Это отдельный артефакт `work/<dataset_hash>/index.json`, строящийся из леджера **до** любой работы
с документами:

**Леджер шире задания, и это не аномалия.** В публичном наборе 1473 строки, 561 `account_id` и
столько же scenario-подобных идентификаторов, из которых в шаблоне только 12. Остальные 549 —
фоновые счета с идентификаторами вида `9001`, `9002`; на них приходится 800 строк из 1473, то есть
**больше половины леджера к заданию не относится**. Поэтому целевое множество задаёт шаблон, а не
леджер, и сверка множеств «леджер == шаблон» неверна: она сработала бы алярмом на первом же
прогоне.

1. Целевые `scenario_id` = ключи `submission_template.json`. Это единственный источник истины о
   том, на кого мы отвечаем.
2. Из каждого `txn_id` извлекается `scenario_id` — единственное место в пайплайне, где `txn_id`
   разбирается. Паттерн выводится из данных, а не зашит как `TXN-<sc>-<n>`.
3. Индекс строится **только для целевых сценариев**. Каждый обязан быть связан ровно с одним
   `account_id`; ноль — жёсткий алярм (мы не найдём ни строк, ни документов), больше одного —
   тоже, потому что `CASE.ru.md:77` гарантирует однозначность.
4. Обратная единственность проверяется **внутри целевого подмножества**: ни один целевой
   `account_id` не делится между двумя целевыми сценариями.
5. Всё остальное — фон. Не ошибка, не карантин, просто число в sanity-отчёте: сколько фоновых
   счетов и сколько их строк. Резкое изменение доли фона между публичным и приватным набором —
   сигнал, что структура датасета другая.

Документ, указывающий на нецелевой `account_id`, отбрасывается штатно и без алярма: скорее всего
это фоновый шум того же генератора.

После этого строки леджера выбираются по колонке `account_id` (а не разбором `txn_id`), а ответы
пишутся под `scenario_id` из индекса. Разделение намеренное: разбор идентификатора — хрупкая
операция, и она выполняется один раз в проверяемом месте, а не на каждом обращении к леджеру, как
сейчас в `engine.py`.

### 5.2.1. Маршрутизация документов и редакции

`account_id` достаётся из текста регуляркой, паттерн которой выводится из данных, а не зашит как
`ACC-\d{4}`. Тип документа, дата и признак «черновик / окончательный» — LLM по строгой схеме.

Привязка документа к счёту строгая, потому что документы грязные и могут упоминать чужие,
вспомогательные или несколько счетов:

- кандидатами считаются только **целевые** `account_id` — те, что есть в индексе, а не все счета,
  встречающиеся в леджере (в публичном наборе это 12 против 561). Упоминание фонового или
  несуществующего счёта игнорируется и пишется в трейс;
- ровно один кандидат → привязка;
- несколько кандидатов → **автоматическая сшивка запрещена**. Разрешение отдаётся LLM с явным
  вопросом «чей это документ», ответ обязан цитировать фрагмент, и ячейка помечается алярмом
  `ambiguous_routing`;
- ноль кандидатов → документ в карантин, алярм. Он не теряется молча: возможно, счёт лежит на
  слепой странице и появится после vision.

Действующая редакция среди документов одного типа для одного счёта: последняя по дате, при этом
явный маркер «окончательный» / «черновик» в тексте перебивает дату. Отброшенные редакции попадают
в трейс с причиной отбрасывания.

### 5.3. Спека ковенанта

Номера пунктов обнаруживаются в тексте договора, а не берутся из литерала. На каждый пункт LLM
выдаёт по схеме:

```json
{
  "clause": "6.1",
  "quote": "<дословная цитата пункта>",
  "metric": "<DSL-выражение>",
  "direction": "max",
  "limit": 9.00,
  "trigger": "<DSL-выражение + сравнение> | null",
  "confidence": 0.87
}
```

`quote` обязателен: он и есть трейс, и он же позволяет верификатору проверить спеку против текста,
не перечитывая PDF.

### 5.4. DSL

Маленький и тотальный. Выполнение произвольного кода не допускается — это дыра и в детерминизме,
и в безопасности. Всё, что выдала модель, парсится грамматикой до исполнения.

```
expr    := agg(category, sign, filters?)
         | doc(fact_key)
         | ratio(a,b) | sub(a,b) | add(a...) | max(a...) | min(a...) | const(x)
sign    := out | in | net
filters := period(from,to) | quarter(n) | counterparty_in(set) | txn_in(ids)
         | min_amount(x) | desc_contains(s)
set     := related_parties | unrestricted_subsidiaries | [литеральный список]
```

Два примитива не косметические:

**`doc(fact_key)`** — число приходит из документа, а не из леджера. Без него ячейка P5 6.1 не
берётся в принципе: договор ACC-7805 п.6.1 требует консолидированный CapEx Группы по отчётности
конечной материнской компании, которого в леджере заёмщика физически нет (в леджере 1.70 млн,
в ключе показатель 9.45 против порога 9.00). Сюда же уезжают `severance_liability` и добавки к
EBITDA, которые сейчас живут константами в `facts.py`.

**`sign: net`** — прямо чинит потерю сторно и возвратов. Сейчас `totals` суммирует только
`amt < 0`, и «Payroll advance recovered» +11.16 млн у P7, «Rent deposit returned» +3.68 млн у B4,
«Tax assessment reversal» +1.18 млн у B1 просто исчезают. Спека обязана явно сказать `out` или
`net`; для расходных категорий по умолчанию `net`.

Валидация: разбор грамматикой, проверка каждой категории против закрытой таксономии, проверка
существования каждого `fact_key` в досье. Любой сбой — фолбэк (см. 5.7).

Каждая из 14 существующих метрик обязана выражаться в DSL и давать бит в бит тот же результат.
Это их регрессионный тест и одновременно приёмка DSL.

### 5.5. Таксономия категорий

Двухуровневая. Листья: `REVENUE`, `PAYROLL`, `UTILITIES`, `RENT`, `TAX`, `INTEREST`, `CAPEX`,
`INSURANCE`, `FINANCING`, `OTHER_OPEX`, `OTHER`. Роллапы определены один раз явно, например
`OPEX_TOTAL = PAYROLL + UTILITIES + RENT + INSURANCE + OTHER_OPEX`. DSL умеет ссылаться и на
листья, и на роллапы.

Причина: сейчас `ebitda = revenue − totals["OPEX"]`, где `OPEX` — отдельная категория наравне с
`PAYROLL` и `RENT`, то есть зарплата в EBITDA не вычитается. На публичном наборе сходится, но это
может быть свойством генератора. Двухуровневая таксономия перекладывает выбор на спеку: договор
сам скажет, что он имел в виду, вместо того чтобы мы угадывали один раз на всех.

Категоризация: правила первым ярусом (детерминированно, быстро, читаемо в трейсе), непокрытое →
LLM пачками по 50 описаний с кэшем. Отчёт покрытия считается по **доле суммы**, а не по числу
строк. `OTHER` — корзина для неразнесённого, она не входит ни в один роллап; любая сумма в ней
означает, что часть расхода потерялась. Алярм срабатывает, когда доля `OTHER` в сумме леджера
заёмщика превышает порог, и повышается до критического, если хоть один ковенант этого заёмщика
ссылается на `OPEX_TOTAL` или на категорию, куда эти строки могли попасть. Сейчас `OTHER` не
входит ни в одну метрику, то есть расход исчезает бесшумно и завышает EBITDA; на публичном наборе
в `OTHER` ровно 0 строк, поэтому дыра невидима.

### 5.5.1. Валютная нормализация

`CASE.ru.md:84` требует суммы в долларах, а леджер мультивалютный (`CASE.ru.md:27`): в публичном
наборе 28 строк `EUR` из 1473, но **у целевых заёмщиков их только 15** — остальные 13 лежат в
фоновых счетах (раздел 5.2), и курс для них не нужен. Распределены по 11 сценариям из 12, без
`EUR` только `P4`. Откуда брать курс, задание не говорит — значит он в документах, и это ещё один
канал извлечения, а не деталь реализации. Сейчас курс задан ровно для одного заёмщика и выведен из
пары платежей вручную.

Контракт в досье:

```json
"fx_rates": [
  {"currency": "EUR", "usd_per_unit": 1.1600,
   "effective_from": "2025-01-01", "effective_to": "2025-12-31",
   "source_quote": "<цитата из документа>",
   "derivation": "table" | "paired_payment"}
]
```

Решения, зафиксированные явно, чтобы не выяснять их 9 августа:

- **Направление** закодировано в имени поля: `usd_per_unit` — сумма в валюте умножается на него.
  Поля `rate` не существует, потому что «курс 1.16» читается в обе стороны.
- **Момент конвертации** — при загрузке леджера, до любой агрегации. Ниже по течению долларовые
  все числа без исключения, и ни одна метрика про валюты не знает.
- **Период** учитывается: строка конвертируется по курсу, чей интервал накрывает её дату. Если
  курс один и без интервала — считается действующим на весь период с пометкой в трейсе.
- **Несколько или противоречивые курсы на одну валюту и дату** разрешаются детерминированно **и**
  поднимают алярм — это не выбор между «упасть» и «промолчать». Правило: последний по дате
  документа; при равных датах — по возрастанию хеша документа. В трейс попадают все кандидаты с
  цитатами, чтобы человек мог пересмотреть выбор в окне 9 августа.
- **Проверка покрытия до расчёта, а не по факту падения.** Для каждого **целевого** заёмщика
  множество пар (валюта, дата) из его строк обязано быть покрыто курсами. Фоновые счета в проверку
  не входят: требовать курсы для них означало бы гарантированный ложный алярм. Непокрытая валюта —
  алярм уровня заёмщика, потому что бьёт сразу по нескольким ковенантам, а не по одной ячейке.

**Фолбэк при отсутствующем курсе — не фолбэк ячейки.** Уронить ячейку из-за одной строки в 2% —
плохая сделка по шкале: ошибка в `actual` штрафуется линейно, а потерянная ячейка стоит целиком.
Лестница: курс из досье этого заёмщика → курс той же валюты из досье **любого другого целевого**
заёмщика этого набора (генератор один, курс скорее всего общий) → и только если валюта не
встретилась нигде, строка исключается с алярмом. Подстановка `1.0` не является ступенью лестницы
ни при каких условиях: она молча занижает сумму примерно на 16% и выглядит как нормальный
результат.

Донор выбирается тем же детерминированным правилом, что и конфликтующие курсы выше: последний по
дате документа, при равенстве — по возрастанию хеша документа. Формулировка «курс любого другого
заёмщика» без тай-брейка означала бы недетерминированный выбор при нескольких донорах с разными
курсами, что противоречит разделу 3.

Конвертация — `Decimal` построчно, агрегация после неё в порядке `txn_id` (раздел 3).

### 5.6. Улика

`CASE.ru.md:103-109` определяет улику узко, и это определение легко прочитать неправильно.
Улика — транзакция, **чья переклассификация, включение, исключение или исправление приводит к
нарушению**. Транзакция, которая лишь вносит вклад в сумму, уликой не является явным текстом:
«ни самая крупная строка в проверяемой категории, ни последняя перед закрытием периода, **ни та,
что случайно вывела накопленную сумму за порог**».

Отсюда два вывода, и оба отрицают наивный leave-one-out.

**Перебирать все строки леджера нельзя.** Это находит ровно то, что задание запрещает: строку,
случайно перевесившую агрегат. Пример «платежи 550k + 50k при пороге 500k → уликой является 550k»
— контрпример к правилу, а не иллюстрация: без документального решения по этому платежу ожидается
`null`.

**Удалять строку тоже нельзя.** Контрфактуал — откат решения, а не удаление операции, и для
исключений разница принципиальная: исключённой строки в расчёте уже нет, её повторное удаление
ничего не меняет и кандидат теряется. Проверено на `B4 6.1`: строка `TXN-B4-0026` исключена по
отсечению периода, удаление её — пустая операция, а откат исключения переворачивает
`BREACH → COMPLIANT`.

**Корректный алгоритм.** Для `BREACH`-ячейки:

1. Собрать множество кандидатов `D` — транзакции, чьё членство в ограничиваемой величине или чья
   сумма есть следствие извлечённого документального решения:
   - реклассификация (аудиторский отчёт перенёс операцию в другую категорию);
   - **включение** — контрагент признан связанной стороной по KYC либо дочка признана
     необременённой, и именно поэтому операция попала в ограничиваемый набор;
   - исключение (отсечение периода, переход рисков);
   - исправление суммы (записка казначейства).
2. Для каждого кандидата **откатить именно его решение** и пересчитать. Контрфактуал зависит от
   типа решения, и «удалить строку» подходит только одному из четырёх:

   | Решение | Откат |
   |---|---|
   | реклассификация | вернуть исходную категорию |
   | включение | исключить операцию из ограничиваемого набора |
   | исключение | вернуть исключённую операцию в расчёт |
   | исправление суммы | вернуть исходную сумму |

3. Ровно один кандидат переворачивает вердикт → он и есть улика. Ноль или больше одного → `null`.

Для `COMPLIANT` улика всегда `null`.

**Покрытие на публичном ключе.** Улика заполнена в 9 ячейках из 36. Три (`B1 6.1`, `P2 6.1`,
`P2 6.3`) объясняются реклассификацией напрямую. Оставшиеся шесть (`P5 6.3`, `P6 6.1`, `P7 6.3`,
`P8 6.3`, `P9 6.1`, `P9 6.3`) — ковенанты по связанным сторонам и необременённым дочкам, где
документальное решение не помечает транзакцию, а **определяет её попадание в набор**: платёж
ограничен ровно потому, что KYC признал контрагента связанным. Это и есть «включение» из перечня.
Ни одна из 9 не объясняется вкладом в агрегат — все девять алгоритм достаёт.

**Перегенерация измерена и принята сознательно.** Откат решения переворачивает вердикт ещё в трёх
ячейках, где ключ содержит `null`: `B4 6.1` (откат исключения), `P7 6.1` и `P8 6.1` (откат
исправления суммы). Правила подавления, отделяющего их от девяти настоящих, вывести не удалось.
Ближайший кандидат — «коэффициентные тесты всегда `null`», прямо по формулировке
`CASE.ru.md:111`, — разбивается о собственные данные: `B1 6.1` (`icr` = EBITDA / проценты) и
`P7 6.1` (налоги+коммунальные / EBITDA) обе `BREACH` и обе коэффициентные, но улика есть только у
первой. Подавление и не нужно — оно было бы чистым убытком.
По `CASE.ru.md:112` в ячейках с `null` в ключе присланное значение не учитывается вообще, то есть
все три ложных срабатывания стоят **0.00**, а одна пропущенная улика в ячейке с непустым ключом
стоит 0.20. При такой асимметрии алгоритм обязан быть щедрым внутри `D` и строгим на её границе.

**`doc()`-метрики.** Метрика, ни одна ветка которой не читает леджер, кандидатов не даст и получит
`null` — это правильный ответ: `evidence_txn_id` есть идентификатор транзакции, и если нарушение
вызвано документальным обязательством, а не операцией, улики не существует. Правило касается
только чисто документарных метрик; смешанные под него не подпадают. Проверка «метрика читает
леджер хоть где-нибудь» делается обходом дерева DSL, а не эвристикой.

**Инвариант — про границу `D`, а не про количество.** На публичном наборе алгоритм даёт 12 улик
при 9 в ключе, и это норма, а не дефект (см. выше). Проверяется не число, а происхождение: каждая
выданная улика обязана быть кандидатом из `D`, то есть иметь конкретное документальное решение и
цитату в трейсе. Улика без такого происхождения — жёсткий алярм: в `D` протёк обычный вкладчик в
агрегат, и это единственная ошибка, которая здесь реально стоит баллов. Отдельный диагностический
счётчик — доля улик, выданных при `null`-подобных метриках; резкий рост означает, что `D` собрано
слишком широко, даже если формально всё легально.

Расширять `D` «на всякий случай» нельзя: кандидат вне `D` не бывает правильным ответом ни в одной
ячейке, а внутри `D` щедрость бесплатна.

### 5.7. Фолбэки

Пустая ячейка и неверная стоят одинаково — ноль. Значит исключение в одной ячейке не имеет права
уронить прогон, и каждая ячейка обязана получить ответ, даже грубый.

Лестница сверху вниз: спека не распарсилась → шаблон по сигнатуре → эвристика по типу ковенанта →
статус по эмпирическому приору плюс `limit` из спеки, если порог удалось прочитать, иначе медиана
`actual` по уже посчитанным ячейкам с тем же направлением сравнения в этом же прогоне. `null` в
`actual` не существует как состояние.

Приор — не литерал. В публичном ключе 17 `BREACH` против 19 `COMPLIANT`, то есть «безопасного»
дефолта не существует и константа `COMPLIANT` не покупает ничего. Приор считается из публичного
ключа скриптом на этапе сборки и условен по тому, что удалось узнать о ячейке: направление
сравнения и семья метрики (коэффициент / абсолютная величина / доля от выручки). Когда неизвестно
и это — глобальная доля, и ячейка помечается алярмом: она подбрасывание монеты и должна
разбираться первой.

Условиться по **номеру пункта** нельзя, хотя сигнал там сильный (6.1 — 10 `BREACH` из 12, 6.2 —
10 `COMPLIANT` из 12). Во-первых, «номер пункта не зашит нигде» — требование раздела 9, и
греп-гейт его поймает. Во-вторых, сигнал конфаундится с типом метрики: в 6.2 почти сплошь
`revenue min` и `capex max`. Приор по семье метрики забирает ту же информацию законным способом.

Каждая ячейка обёрнута индивидуально.

**Триггер решает, применяется ли тест, но не отменяет вычисление.** `CASE.ru.md:96-99` прямо
требует: у ковенантов с оговоркой или условием `actual` — по-прежнему фактическое значение
показателя, «оно может быть выше лимита при статусе `COMPLIANT`. Указывайте именно его, а не
значение условия, и не `null`». Поэтому метрика считается всегда, а триггер влияет только на
вердикт. Формулировка «вычислять после проверки триггера» была бы прочитана как «не вычислять,
если триггер не сработал» — и стоила бы 0.30 плюс 0.20 на каждой такой ячейке. Защита от деления
на ноль решается в интерпретаторе DSL (`ratio` с нулевым знаменателем → помеченное значение и
алярм), а не пропуском вычисления.

**Вердикт — по знаковому значению, вывод — по модулю.** `CASE.ru.md:93` требует, чтобы `actual`
был всегда положительным, «в том числе для расходов; `actual` — это модуль». То есть `abs()` на
выводе не допущение, а требование. Ошибка сегодняшнего кода не в самом `abs()`, а в том, что он
стоит между вычислением и сравнением: `capex/ebitda = 1.7M / −180k = −9.44` даёт `COMPLIANT` при
пороге `max 9.00`, и печатается как `9.44` — число выглядит верным, статус нет. Правильный
порядок: посчитать со знаком → сравнить со знаком, с явной обработкой EBITDA ≤ 0 → взять модуль
при записи в submission. Отрицательная EBITDA при этом сама по себе алярм: это не нормальное
состояние заёмщика, и ячейку надо смотреть глазами.

## 6. Harness

**Submission пишется задом наперёд.** Первым делом по `submission_template.json` на диск кладётся
полностью заполненный скелет — все ячейки с фолбэк-значениями. Каждая успешно посчитанная ячейка
перезаписывает свою. На любой секунде прогона на диске лежит валидный отправляемый файл. Это
превращает «отправлять рано и часто» из намерения в свойство кода. Сейчас наоборот: `json.dump`
стоит после `solve()`, и одно исключение оставляет прошлый submission.

Число ключей в submission равно числу ключей в шаблоне — инвариант, проверяемый перед записью.
Набор заёмщиков и номера пунктов берутся из `submission_template.json`, а не из `SPECS` и не из
литерала `("6.1","6.2","6.3")`.

**Окружение.** Зафиксировать интерпретатор (3.11), venv, `requirements.txt`, `run.sh <архив>` как
единственную точку входа. Сейчас на дефолтном `python3` этой машины (3.9.6) `dossier.py` не
импортируется из-за `str | None` без `from __future__ import annotations`, `pypdf` не установлен,
`requirements.txt` и `run.sh` не существуют, а `__pycache__` собран под 3.14, которого на машине
нет. На чистой машине сейчас не стартует ничего.

**Параллелизм.** Заёмщики независимы. Ограничитель — rate limit Anthropic, не CPU. Замерить
заранее: вызовов на заёмщика × заёмщиков / RPM. Если приватный набор в 10 раз больше публичного —
это разница между 4 и 40 минутами.

**Ретраи и деградация API.** Rate limit — это про пропускную способность, а 429/500/таймаут в
трёхчасовом окне — отдельный сценарий, и поведение в нём описывается здесь, а не выясняется на
месте.

- Ретраится только то, что имеет смысл ретраить: 429, 5xx, таймаут соединения. 400 и ошибка
  валидации схемы — не сетевая проблема, ретрай их не чинит, они идут сразу в фолбэк с записью
  в трейс.
- Экспоненциальный backoff с джиттером, потолок 4 попытки на вызов. Джиттер — из хеша ключа
  кэша, а не из `random()`, иначе ломается воспроизводимость.
- **В кэш попадает только успешный ответ, прошедший валидацию схемы.** Провал не кэшируется
  никогда: иначе одна сетевая икота залипнет в кэше и будет отравлять все последующие прогоны,
  причём молча.
- Исчерпание попыток на одном вызове роняет только свою ячейку (или свой документ), а не прогон.
  Ячейка уходит на лестницу фолбэков и помечается алярмом `api_exhausted` — при переотправке такие
  разбираются первыми, потому что чинятся простым повтором.
- Глобальный потолок стоимости на прогон, при достижении — прогон останавливается штатно и
  дописывает submission из того, что уже посчитано. Скелет с фолбэками на диске уже лежит, так что
  результат остаётся отправляемым.
- Замер на репетиции 8 августа даёт цифру, от которой считается потолок: вызовов на заёмщика,
  токенов на вызов, стоимость полного прогона.

**Трейс на каждую ячейку.** Какие документы взяты и какие отброшены с причиной, категория каждой
транзакции, спека с цитатой, формула, входы, выход, сработавший ярус фолбэка. Это одновременно
отладка и половина третьего критерия оценки.

**Sanity-скрипт.** До запуска пайплайна на новом архиве: `dataset_hash`, сколько целевых
сценариев, **сколько фоновых счетов и какая доля строк на них приходится** (в публичном наборе
549 счетов и 800 строк из 1473 — 54%), сколько документов и каких типов, сколько слепых страниц,
сколько грязных строк, какие валюты и сколько строк в каждой у целевых заёмщиков, какие номера
пунктов — и диф против публичного набора. Всё, что «не как в публичном», — список того, что
сломается.

Доля фона вынесена отдельным пунктом намеренно: это самое крупное свойство данных, которое
неочевидно при беглом взгляде на леджер, и цена ошибки здесь — расчёт ковенантов по чужим строкам.

## 7. Eval

Публичный сырой скор почти бесполезен: он подогнан руками через `facts.py` и `SPECS`. По убыванию
ценности:

**1. Экстракционный.** LLM-слой против `eval/expected_extraction.py`. Меряет ровно ту часть,
которой сейчас не существует и которая провалится 9 августа. Отдельно по фактам досье и отдельно
по спекам (метрика, направление, порог).

**2. Переименование и сдвиг порогов.** Две мутации публичного набора, и обе — потому что новый
ключ выводится **без** нашего движка.

- Переименование компаний, контрагентов и дочек: ни одно число не меняется, ключ остаётся прежним
  байт в байт. Ловит единственное, что экстракционный eval поймать не может, — знание, зашитое
  мимо слоя извлечения: имя в промпте, регулярка под `Capital`, шаблон, сматчившийся по названию.
- Сдвиг порога в тексте договора (`9.00x → 6.50x`): новый статус выводится сравнением *старого*
  `actual` из ключа с новым порогом. Ловит «модель вспомнила порог, а не прочитала его».

Более сложные мутации (подмена окончательного отчёта, ковенант от другого заёмщика, лишний пункт
6.4) отвергнуты сознательно: их ключ пришлось бы пересчитывать нашим же движком, то есть тест
проверял бы самосогласованность, а не правильность. Номера пунктов и число ячеек покрываются тем,
что обход идёт по шаблону, — это свойство кода, а не тест.

**3. LOBO.** 12 прогонов, каждый раз один заёмщик скрыт из промптов и библиотеки шаблонов. Ловит
шаблон, подогнанный под конкретного заёмщика.

**4. Инварианты.** Дешёвые детерминированные проверки, ловящие почти все катастрофы:

| Проверка | Что ловит |
|---|---|
| У каждого сценария есть договор; имя заёмщика в договоре == имени в KYC | сшивку не того досье |
| Каждая реклассификация из окончательного отчёта применилась к какой-то строке | несовпадение имён контрагентов (`Ertis Capital, LLP` vs `Ertis Capital LLP`) |
| Сумма разнесённого == сумме леджера по заёмщику | потерянные строки |
| У всех ячеек `actual` конечен и не `null` | пустые ячейки |
| `BREACH` и ровно один переворачивающий контрфактуал внутри `D` → улика не `null` | пропущенные улики |
| Ровно один действующий договор на счёт | не отфильтрованную редакцию |
| Число ключей в submission == числу ключей в шаблоне | −0 за переименование |
| Каждый сценарий шаблона связан ровно с одним `account_id`; внутри целевого подмножества счета не делятся | ответы под чужим ключом |
| Каждая пара (валюта, дата) у целевых заёмщиков покрыта курсом | тихое занижение валютных сумм |
| Каждая выданная улика — кандидат из `D` с цитатой решения в трейсе | улику подменил вкладчик в агрегат |
| Доля фоновых счетов и их строк в пределах ожидаемого | другая структура датасета |
| Доля суммы в `OTHER` по категориям, которые трогают ковенанты | тихо исчезающий расход |

Проверка про реклассификации — самая ценная: так ловится промах, который иначе не виден никак.

**5. Греп-гейт.** Ни одного имени заёмщика, номера пункта, порогового числа, префикса `TXN-` или
`ACC-` в промптах и коде вне тестов и eval. Секунда на прогон, ловит больше, чем половина мутаций.

**Скорер повторяет официальную формулу без вариантов.** Двусмысленности в правиле про улику нет:
`CASE.ru.md:111-116` говорит, что в ячейках с `null` в ключе присланное значение **не учитывается
вообще, в том числе `null`**, а 0.20 масштабируются точностью `actual`. Никаких оптимистичной и
пессимистичной границ строить не нужно — это выдуманная неопределённость, которая порождала бы
ложные регрессии. Единственная реальная неизвестная — веса ячеек по сложности
(`CASE.ru.md:129`), и их подобрать нельзя; поэтому локальный скор трактуется как сырая сумма и
сравнивается только сам с собой между прогонами.

Скорер обязан печатать `evidence_txn_id` — сейчас не печатает, из-за чего расхождения в ячейках с
непустым ключом не видны.

Метрика для оптимизации — не сырой скор, а ожидаемый балл под неопределённостью. Из шкалы два
неочевидных вывода: статус — всё или ничего, хеджировать нельзя, при сомнении выбирать более
вероятный, а не «безопасный» `COMPLIANT`; `actual` — по убывающей шкале, поэтому грубая оценка
всегда лучше пустоты.

## 8. Порядок работ

Работа идёт одним человеком с флотом сабагентов. Контракты раздела 5 написаны первыми
намеренно — они и есть интерфейс между параллельными потоками.

### 6 августа, с 11:15 — фундамент

Не параллелится, от него зависят все потоки. Это единственный день, где последовательность
обязательна, поэтому он и стоит первым: три потока 7 августа физически не стартуют, пока
контракты раздела 5 не существуют в коде.

- окружение, `run.sh`, зафиксированные зависимости
- скелет harness: стадии, артефакты, content-addressed кэш, fail-open обёртка на ячейку,
  скелет-первым submission
- обход ячеек по `submission_template.json`
- скорер по официальной формуле, с печатью `evidence_txn_id`
- индекс `account_id → scenario_id` из леджера с проверкой единственности (см. 5.2)
- `facts.py` и `SPECS` → `eval/expected_extraction.py`

- скрипт, считающий эмпирический приор статусов из публичного ключа (см. 5.7)

**Гейт фундамента.** `run.sh` на публичном архиве даёт валидный JSON, воспроизводит текущие
34.00. Это регрессионный якорь на всё дальнейшее.

Гейт не пройден к концу дня 6 августа — потоки 7 августа не запускаются, а вместо этого фундамент
доделывается утром 7-го, и из плана вылетает поток Eval целиком (он самый отложимый: без него
пайплайн работает, просто вслепую). Порядок жертв при отставании, от первой к последней:
мутации → LOBO → библиотека шаблонов (остаётся голый DSL) → vision-ветка. Инварианты, фолбэки и
скелет-первым submission не жертвуются ни при каких условиях — они стоят между «плохой результат»
и «нулевой результат».

## 9. Ставка на генерализацию

На 12 заёмщиках — 14 разных формул, повторов почти нет. Генератор явно тянет из большого пула
шаблонов, значит в приватном наборе будут типы ковенантов, которых мы не видели. Хардкод умрёт.
Но и чистый «LLM пишет формулу» даёт вариативность там, где нужен цент в цент.

Отсюда гибрид: сигнатура спеки совпала с шаблоном из библиотеки → вылизанная реализация; не
совпала → выражение на DSL, проверенное грамматикой; не распарсилось → лестница фолбэков.

Ничего в коде не зашито под: 3 пункта на заёмщика, 12 сценариев, номера `6.1–6.3`, `USD`/`EUR`,
русский язык, `ACC-\d{4}`, префикс `TXN-`.

Реальные кандидаты на сюрприз 9 августа:

- Кратно больше заёмщиков — параллелизм и стоимость становятся критичными.
- Другие номера пунктов (`7.2`, `5.4`) — шаблон говорит «номер пункта», не «6.x».
- Казахский язык: в наборе есть `CASE.kz.md`, документы могут быть двуязычными.
- Больше одного платежа связанной стороне: кандидатов в `D` окажется несколько, улика станет
  `null`. Это правильный ответ по определению (раздел 5.6), но в публичном наборе такого случая
  нет, поэтому проверить отдельно на мутации.
- Настоящая таблица курсов вместо выведенного из пары платежей: ветка `derivation: "table"`
  раздела 5.5.1 на публичном наборе не исполняется ни разу.
- Валюта помимо `EUR`, либо `EUR` у заёмщика, в чьих документах курса нет вовсе.
- Массовые сканы — бюджет vision.

## 10. Открытый вопрос

Ячейка P4 6.3 на публичном наборе не сводится к багу в коде. У P4 ровно одна строка выручки
(`TXN-P4-0043` = 7 004 318.47) и ровно один платёж связанной стороне (`TXN-P4-0048` = 288 417.52);
KYC даёт порог связанной стороны 30%, доля Aral Capital Partners — 33.4%. Отсюда 0.041177 > 0.04 →
`BREACH`, ключ же говорит `COMPLIANT` при `actual` 0.04. Чтобы сойтись, знаменатель должен быть
≥ 7 210 438 либо числитель ≤ 280 172.74. Нужного числа нет ни в одном текстовом слое — оно на
страницах 3–4 `2ed0b2ee4b57.pdf`, которые `pypdf` не отдаёт.

Ожидание: постраничный детектор слепоты плюс vision (раздел 5.1) закроют этот пробел
автоматически. Если после включения vision-ветки ячейка всё равно не сходится — разбирать отдельно
7 августа, до того как строить на этом библиотеку шаблонов.
